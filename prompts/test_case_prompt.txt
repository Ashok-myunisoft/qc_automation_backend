#SCREEN STRUCTURE — TABBED VS. DIRECT (CRITICAL — READ FIRST)

Before writing anything, check `screen_sections` in the Project Analysis
for this screen's page.

CASE A — `screen_sections` is empty (or absent): this is a DIRECT screen —
a plain form with no tabs, steps, wizards, or accordions. Write the
feature file exactly as you always have: one flat list of
Scenario/Scenario Outline blocks directly under Background. Do NOT
introduce any grouping keyword for a screen like this — a small 5-10
field form has no sections to group by, and adding a grouping structure
here would be inventing structure the screen doesn't have.

CASE B — `screen_sections` contains one or more entries: this is a
TABBED screen — the screen is genuinely organized into tabs, steps, or
similar activation-gated sections (this is common on large ERP master
screens, e.g. a 14-tab Item Master). For a screen like this:

- Emit one Gherkin `Rule:` block per entry in `screen_sections`, in the
  same order those sections appear in the Project Analysis.
- Label each `Rule:` with that section's `section_label` exactly as
  given (e.g. `Rule: Purchase`, `Rule: Quality&Service`) — do not rename,
  abbreviate, or append extra words like "tab" unless `section_label`
  itself already contains that word.
- Within a `Rule:` block, write ordinary `Scenario:` / `Scenario Outline:`
  blocks exactly as you would for a direct screen — the only thing that
  changes is that they are now grouped and labeled by section.
- Fully exhaust one section's own fields (per that section's
  `contains_control_names`), validations, and conditional logic — per
  the #SCENARIO DEPTH rules below — before starting the next `Rule:`
  block. Do not interleave two sections' scenarios.
- Fields, business actions, or dialogs that are NOT tied to any specific
  section (i.e. shared/header-level, appearing before any tab in the
  source, such as a screen's top identity fields or its Save/Delete/
  AddNew actions) do not belong inside any one `Rule:` block — write
  their scenarios directly under `Background`, before the first `Rule:`
  block, the same way a direct screen would.
- The number of `Rule:` blocks you emit must equal the number of entries
  in `screen_sections` — never fewer, and never merge two sections into
  one `Rule:` block even if their labels look similar.

Never use `Rule:` for a Case A screen, and never skip `Rule:` grouping
for a Case B screen just because a section looks small — every section
listed in `screen_sections` gets its own `Rule:` block regardless of how
many fields it contains.

#SCENARIO DEPTH (CRITICAL — NO FIXED SCENARIO COUNT)

There is no fixed target scenario count for a feature file, and no fixed
count per Rule block. The right number of scenarios is whatever the
Project Analysis actually justifies — never pad toward a number, and
never cap short of one. This means:

- A simple direct screen (Case A above) with 5-10 fields and no tabs may
  correctly produce as few as 10-15 scenarios. That is correct and
  complete if that is genuinely everything the screen supports — do not
  invent extra scenarios just to reach a larger number.
- A large tabbed screen (Case B above) with many sections and 100+
  fields may correctly produce 100 or more scenarios once every section
  is fully exhausted. That is correct and expected, not excessive — do
  not stop early or thin out coverage on later sections just to keep the
  total number down.
- Within EACH section of a tabbed screen (or across the whole screen for
  a direct one), reach full depth by exhausting the real signal already
  present in Project Analysis, not by inventing behavior:

  - Every field's validations (required, length, regex, format) → both a
    positive and a negative scenario, per field, where the Project
    Analysis reports that validation.
  - Every entry in conditional_business_logic that affects fields in
    this section → its own scenario per branch (the condition true, and
    the condition false, when both are observable).
  - Every dialog tied to this section → both its confirm path and its
    cancel path as separate scenarios, where the Project Analysis
    reports both buttons.
  - Every loop tied to this section → add-row, remove-row, and (if
    is_bounded) the max-rows boundary case, as separate scenarios.
  - A screen_section with activation_required=true → a scenario
    confirming fields inside it are only interactable after activation.
  - Every business_action → at least one workflow scenario, plus a
    negative/error-path scenario if Project Analysis describes one.
  - Every event_handler with a meaningful "conditions" branch that
    affects fields in this section → its own scenario per branch.

HARD RULE: no two scenarios may exercise the same field/action/condition
combination in the same way, anywhere in the feature file — including
across different Rule blocks. If a scenario would be a near-duplicate of
one already written (same field, same validation, same outcome), do not
write it — find the next genuinely distinct case instead, or move on if
that section (or the whole screen, for a direct screen) has been fully
exhausted.

# FUNCTIONAL BEHAVIOR COVERAGE

Use the `functional_behavior` section of Project Analysis as a primary source
for behavior-driven scenarios. For a tabbed screen, place each resulting
scenario inside the `Rule:` block for the section it actually affects; if
a behavior is screen-wide rather than tied to one section, place it under
Background scenarios instead, same as shared fields/actions.

For every applicable item in `functional_behavior`:

- lifecycle_hooks:
  Create scenarios for meaningful user-observable initialization or
  lifecycle behavior when it can be triggered/verified through the UI.

- event_handlers:
  Generate scenarios for each meaningful user-triggered event and business
  action described in the event handler analysis.

- conditional_business_logic:
  Generate positive and negative scenarios for each meaningful condition
  that changes field behavior, business actions, or UI outcomes.

- frontend_service_calls:
  Generate scenarios that verify the UI behavior associated with each
  frontend service call, including success and error handling when the
  Project Analysis explicitly describes those outcomes.

- data_transformations:
  Generate scenarios that verify transformed/derived values when those
  transformations produce observable UI or business behavior.

- functional_summary:
  Use this as the end-to-end behavioral context for connecting individual
  scenarios into realistic user workflows.

Do not create scenarios for internal implementation details that have no
observable or testable frontend behavior.
Do not invent API responses, backend behavior, or outcomes that are not
described in Project Analysis.

#CRUD WORKFLOW ORDER (CRITICAL — always follow this sequence)

CRUD scenarios must always appear in this exact order, both at the
feature level (for direct screens) and within each Rule: block (for
tabbed screens). Never place Update before Create, never place Delete
before Read, never place validation scenarios before the basic positive
Create scenario:

1. SMOKE — verify the screen loads and navigation works
2. CREATE (positive) — click Add New / ➕ button first, fill all
   required fields, click Save, verify success message
3. CREATE (negative/validation) — required field missing, invalid
   format, duplicate constraint, boundary violations
4. READ/VIEW — search or select an existing record first (via Item
   Code, lookup, or search field as shown in Project Analysis), then
   verify field values display correctly
5. UPDATE — select an existing record first (same as Read), modify
   one or more fields, click Save, verify success message
6. DELETE — select an existing record first, click Delete button,
   verify confirmation dialog appears, then:
      - Confirm path: click Confirm → verify deletion success message
      - Cancel path: click Cancel → verify record still exists
7. BUSINESS ACTIONS — Print, Export, Approve, or any other
   business_action from Project Analysis, each with positive +
   negative/error path where applicable
8. EDGE CASES — boundary values, conditional field visibility,
   checkbox states, read-only field verification

CRUD NAVIGATION RULES (same screen pattern — most common in this ERP):

Most screens in this application perform all CRUD operations on the
SAME screen — navigation happens once in Background, then each
operation uses a different trigger:

- CREATE trigger: click the Add New button (➕ or equivalent
  business_action from Project Analysis) to enter create mode BEFORE
  filling any fields. Never write a Create scenario without this
  trigger step first.
- READ/UPDATE trigger: search for or select an existing record using
  the screen's primary key field (Item Code, Employee Code, etc. —
  whatever the Project Analysis shows as the lookup/search field)
  BEFORE viewing or editing. Never write an Update scenario that
  starts directly entering field values without first selecting a
  record.
- DELETE trigger: select the existing record first (same as
  Read/Update), THEN click the Delete button. Never write a Delete
  scenario that clicks Delete without first selecting a record.

For every CREATE scenario, the step sequence must be:
  1. I click the Add New button (or equivalent)
  2. I enter/select field values
  3. I click the Save button
  4. Then I should see "<success message>"

For every READ/UPDATE scenario, the step sequence must be:
  1. I select/search for "<existing record>" in the "<primary key>" field
  2. I verify/modify field values
  3. I click Save (for Update only)
  4. Then I should see "<success/value>"

For every DELETE scenario, the step sequence must be:
  1. I select/search for "<existing record>" in the "<primary key>" field
  2. I click the Delete button
  3. Then I should see "<confirmation message>"
  4. When I click Confirm/Cancel
  5. Then I should see "<result>"

EXAMPLES TABLE LABELING (preferred, not forced): when a Scenario Outline
has an Examples table, add a labeled first column (e.g. "Condition")
giving each row a short, plain-language description of what that row
specifically tests — so the feature file is self-explanatory by reading
down that column alone, without needing to interpret the data values.

Use this whenever a table has more than one row, since that's exactly
when rows need distinguishing. It's fine to omit the label column only
when a table is trivially self-describing on its own (e.g. a single-row
Examples table for one straightforward Create scenario) — don't force a
label column onto something that doesn't need one just to satisfy a rule.

- NAVIGATION STEP ARITY — determined by the Project Analysis, not fixed:
  Check what the Project Analysis actually shows for this screen's location
  in the app hierarchy, and phrase the navigation step to match EXACTLY —
  never default to one shape regardless of the real data:

    * Module -> Screen directly (no intermediate menu/submenu level shown
      in the Project Analysis):
        I navigate through the following path "<Module>" -> "<Screen>"

    * Module -> Menu/Submenu -> Screen (the Project Analysis shows an
      intermediate menu, folder, or submenu level between the module and
      the screen — this is common, not an edge case; do not collapse it
      down to a 2-level path just because that's the more familiar shape):
        I navigate through the following path "<Module>" -> "<Menu>" -> "<Screen>"

  Use whichever arity the Project Analysis actually shows for THIS screen
  — 2 parts or 3 parts — and never pad a real 2-level path to 3, and never
  collapse a real 3-level path down to 2. Keep that same arity and exact
  phrasing consistent across every scenario in the one feature file you're
  generating (including inside every Rule block, for a tabbed screen),
  since ScriptGenerateAgent (the next agent in the pipeline) implements
  exactly one navigation step handler per feature, matching whichever
  arity your Background step uses — a feature that mixes both shapes, or
  uses the wrong one for what the Project Analysis actually shows, will
  fail at that step.
