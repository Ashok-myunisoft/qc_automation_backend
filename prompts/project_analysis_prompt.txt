--------------------------------------------------
PRIMARY SCREEN vs. REFERENCE MATERIAL (CRITICAL)
--------------------------------------------------

The supplied source is NOT all one page. It contains two different kinds
of content, and confusing them produces a wrong analysis:

1. The files under "primary_dir" — this, and ONLY this, is the actual
   screen/page you are analyzing. Every field, page_name, navigation_path,
   business_action, table, dialog, screen_section, and functional_behavior
   entry you report must come from what this screen ACTUALLY does.

2. Every other file supplied (shared library components such as
   gb-picklist, gb-checkbox, gb-dialog, formjson config files, i18n
   translation files, or any other file outside primary_dir) exists
   SOLELY so you can find the real data-cy/id/name attribute, real field
   identity, or real translated label text that a field or button
   actually uses when the primary screen's own file only references it
   indirectly (e.g. `<gb-picklist controlName="DomainCode">`, or
   `{{ 'PARTY_TYPE' | transloco }}`) without showing the rendered value
   itself. Use these files ONLY to fill in accurate values for
   fields/actions that genuinely belong to the primary screen.

Do NOT do any of the following, even though the reference files' content
may be substantial or look like a complete page of its own:
- Do NOT treat a reference file's own page/component (e.g. a shared
  dialog box's "Close" button) as if it were a page or field of the
  screen you are analyzing, unless the primary screen's own file
  genuinely uses that exact component for that exact purpose.
- Do NOT let a reference file's content override, replace, or merge with
  the primary screen's own page_name, navigation_path, or business logic.
- Do NOT produce an analysis that is actually about a reference component
  instead of the primary screen — if primary_dir's own files reveal very
  little (a thin routing/report file, for instance), report what little
  is genuinely there rather than substituting a more detailed reference
  file's content as if it were the primary screen.

IMPORTANT EXCEPTION — shared-component-owned behavior tied to a primary
screen's own business action: some behavior that genuinely belongs to the
primary screen (a confirmation dialog for Delete/Clear/AddNew, for
example) is implemented ENTIRELY inside a shared component's own handler
code (e.g. inside gb-formaction.component.ts's click handler for the
Delete button) rather than anywhere in the primary screen's own file. This
is NOT the same thing as "reference file's own unrelated page/component"
described above — it is the real implementation of something the primary
screen's own business action triggers. See DIALOG ANALYSIS below for how
to find and report this correctly. Resolving this is still locator/behavior
resolution for a primary-screen action, not scope creep into the reference
file's own content.

COMPONENT COVERAGE (CRITICAL — READ BEFORE ANALYZING ANYTHING)
--------------------------------------------------

This analysis is the FOUNDATION every downstream agent builds on — Test
Planning, Test Case Generation, Feature File Generation, and Script
Generation all treat your output as ground truth and do not re-read the
source themselves. A field, action, locator, or piece of screen structure

completeness here matter more than anywhere else in the pipeline.

Full coverage means:

- Every distinct interactive component instance actually present in the
  primary screen's own template must be enumerated — not just one example
  of each category. If a screen has three separate picklist fields, three
  radio groups, and two grids, all of them are reported individually, not
  summarized as "several picklist fields exist."
- Do not stop at the categories explicitly named elsewhere in this prompt
  (forms, tables, dialogs) if the primary screen contains other
  interactive structures — tabs, accordions, steppers, conditional
  sections (*ngIf-gated blocks), embedded sub-forms, toggle panels, or any
  other component that a user can interact with. Tabs, steppers, and
  accordions specifically MUST be reported under SCREEN SECTIONS below,
  not folded silently into other_components, because they gate whether
  their contained fields even exist in the DOM yet (see that section).
  Anything else that doesn't fit an existing category goes in
  "other_components".
- When the primary screen's own file references a shared/library
  component (gb-newpicklist, gb-formaction, gb-formgrid, gb-dialogbox, or
  any other Gb component) without itself showing the rendered data-cy/id,
  resolve that component's OWN template as deep as necessary to find the
  real locator — one hop is frequently not enough. A module file
  (`gb-formgrid.module.ts`) commonly re-exports a component file
  (`gb-formgrid.component.ts`) whose own template is where the real,
  index-bound attribute actually lives. Follow the chain until you reach
  the file that actually contains the attribute, not just the first file
  that mentions the component's name.
- The project's source is organized with per-screen source under
  `projects/{app}/{category}/{screen}/` and shared library source under
  `libs/` and `features/`. Files under `projects/...` matching primary_dir
  are the primary screen; files under `libs/`/`features/` (or a different
  `projects/...` path) referenced FROM the primary screen are reference
  material to resolve locators/behavior from, per the PRIMARY SCREEN
  section above.
- Not every screen uses the app's own Gb-prefixed component library. Some
  screens use raw Angular Material components directly (`mat-select`,
  `mat-radio-group`, `mat-checkbox`, `mat-datepicker`, `mat-slide-toggle`,
  etc.) with no Gb wrapper at all. This is a legitimate, different pattern
  — not a gap or an error in the source. See COMPONENT CLASSIFICATION
  below for how to report these.
- If, after following the reference chain as deep as the supplied source
  allows, a locator still cannot be found, do NOT fall back to guessing
  from the visible label or the component's tag name. Set that specific
  locator field to "Unknown" and add the unresolved component/file to the
  "unresolved" list at the end of the output. Guessing a plausible-looking
  data-cy is worse than reporting Unknown — a downstream script built on a
  guessed locator fails silently at test-run time, while "Unknown" is
  visible and actionable immediately.

FORM CONFIG (formjson) RESOLUTION — CRITICAL, READ BEFORE FIELD/GRID ANALYSIS
--------------------------------------------------

Many shared components render data-cy, field identity, and even field
EXISTENCE dynamically from a runtime config object, not from anything
visible in the primary screen's own .ts/.html or even from the shared
component's own template. This project keeps that config in a per-screen
JSON file at `projects/{app}/{category or similar}/public/formjson/
{screen}.json`. Treat this file as REQUIRED reference material — same
resolution priority as any other reference file — whenever any of the
following signals appear in the primary screen's own template or the
shared component's template:

- A shared field component's rendered attribute is built from a "Field"
  or "item" object rather than the literal formControlName — for example
  `newpicklist.component.ts` builds its real data-cy from
  `Field.Name + GridIndex`, not from the formControlName string you can
  see in the primary screen's template. Field.Name is NOT guaranteed to
  equal the formControlName. You MUST open the matching formjson's
  ObjectFields entry (matched by LinkId/Name) to confirm the real value —
  never assume they match just because they look similar.
- A grid/repeating component (gb-formgrid or similar) is used. Components
  like gb-formgrid are GENERIC: their own template contains no column
  names at all — every column's identity (item.value), data-cy pattern,
  and even which columns exist comes entirely from that field's "Grid"
  array in the formjson config (ObjectFields[n].Grid, an array of objects
  each with a "value" naming one column). This means: for ANY loop driven
  by a generic grid/formgrid component, you CANNOT enumerate the loop's
  "fields" list (per LOOP / REPEATING STRUCTURE ANALYSIS below) from
  Angular source alone — you MUST locate and read the formjson's Grid
  array for that field to know how many columns exist and what each one
  is actually called. Skipping this step is the single most common cause
  of collapsing multiple real per-row fields into one invented field name
  — treat it as a hard requirement, not an optional enrichment.
- If the formjson file for the screen was not supplied alongside the
  primary screen's source, do NOT guess column/field identities from the
  shared component's variable names (e.g. do not report a field literally
  named "item" or "value"). Instead set the loop's "fields" list to a
  single entry noting the Grid array could not be resolved, and add the
  missing formjson path to "unresolved" using the expected path pattern
  (`{app}/public/formjson/{screen}.json`) so the gap is visible and
  actionable.

a translation key.

- If a translation/locale source file is supplied as reference material
  (e.g. an `assets/i18n/en.json`, `*.transloco.json`, or similar
  key-to-string mapping file), resolve the key against it and report the
  real resolved string as the label, exactly as you would resolve any
  other reference-file value.
- If no such translation source is supplied, do NOT invent a plausible
  English label from the key name (e.g. do not turn "PARTY_TYPE" into

  know the difference, since an i18n key is not what actually renders in

  without the real translation. Add the missing translation source file
  to "unresolved".
- This applies uniformly to field labels, business action labels, dialog
  headings/messages, tab/step labels, and any other user-facing text —
  wherever the source uses an i18n pipe instead of a literal string.

NAVIGATION ENTRY TYPE — determine and report how this screen is actually
reached BEFORE building navigation_path, because not every screen is
reachable through the menu tree:

- "menu": the screen is opened by navigating the module/folder/leaf menu
  tree. Build navigation_path as described below.
- "modal_trigger": the screen is a popup/lightbox/dialog opened from
  within another screen's own workflow (for example, a component with no
  gb-formaction of its own, opened via a service call or button click on
  a different screen, not present in any menu tree). For this type, do
  NOT force-fit a fake menu-tree navigation_path — instead report
  navigation_path as an empty array and additionally report, if
  identifiable from source, a "trigger_source" object describing what
  launches it: { "source_description": "", "source_trigger": "" }
  (e.g. source_description: "opened from the Sales Order screen's Bin
  Details action", source_trigger: the method/event name that opens it,
  if determinable from the supplied source — "Unknown" if the launching
  screen was not supplied).
- "embedded": the screen/component is always rendered as a permanent
  part of another screen (not a popup, not independently navigable) —
  report similarly to modal_trigger, with trigger_source describing the
  parent screen/context if determinable.
- "unknown": use only if the supplied source gives no basis to determine
  any of the above; do not default to "menu" just because that is the
  most common case — confirm it from the actual source (does this
  screen's component get instantiated via a menu-tree click path, a
  dialog.open() call from elsewhere, or is it unclear).

Navigation Path (only when Navigation Entry Type is "menu") is NOT a
single flat string — different screens are reached by different numbers
of clicks, and reporting the wrong hop count produces a navigation step
that clicks the wrong element or skips one entirely. Determine the ACTUAL
hop count from the real menu/sidebar source if it is supplied (a
menu-tree component, routing config, or similar) rather than assuming
every screen is a simple two-hop Module -> Screen path. Some screens sit
inside an intermediate menu folder (Module -> Folder -> Screen, a
three-hop path) — if the source shows this, report every hop, not just
the first and last.

Report navigation_path as an ordered list of hop objects, each with:

- hop_label: the visible text/name for this hop
- hop_type: one of "module", "menu_folder", "menu_leaf"
- data_cy: the real data-cy for this hop's clickable element, if found
- id: the real id, if found
- preferred_locator: same priority order as elsewhere (data-cy, then id,
  then name, then other stable selector)

MENU HOP DATA-CY IS OFTEN RUNTIME-COMPUTED, NOT STATIC — READ CAREFULLY:
in a menu-tree component, a hop's data-cy is frequently built from a
runtime tree-depth value rather than a literal number, for example
`[attr.data-cy]="RemoveSpace(node.DisplayName) + '-MenuData' + node.level"`
or `... + '-MenuFolder' + node.level`. The STRING PATTERN
("{ScreenName}-MenuData{level}" / "{FolderName}-MenuFolder{level}") is
resolvable from the menu-tree component's source, but the concrete
numeral for node.level is runtime tree-depth data — it depends on where
THIS SPECIFIC screen sits in the actual menu hierarchy, which the
menu-tree component's own source does not and cannot state. Do not guess
this numeral (e.g. do not assume "0" for a leaf or "1" for a folder just
because that is common). Instead:
- If a definitive menu-hierarchy source is supplied that states the exact
  depth for this specific screen (a menu-data JSON/DB export, a routing
  config enumerating the module/folder/screen tree, or equivalent),
  resolve and report the literal numeral.
- Otherwise, report data_cy using an explicit "{level}" placeholder (e.g.
  "CostAnalysis-MenuData{level}"), exactly as the LOOP section requires
  for index placeholders, and add the missing menu-hierarchy source to
  "unresolved" rather than inventing a numeral.

If the menu/sidebar source needed to confirm hop count and locators
was not supplied alongside the primary screen, report navigation_path
using whatever hop count you can infer, set data_cy/id to "Unknown" on
any hop you cannot confirm, and add the missing menu/navigation source
to "unresolved" rather than guessing a plausible-looking path.

- data-cy
- id
- Preferred Locator (same priority order as FIELD ANALYSIS: data-cy, then

SCREEN SECTIONS (TABS / STEPS / WIZARDS / ACCORDIONS) — CRITICAL
--------------------------------------------------

Some screens gate groups of fields behind a container the user must
explicitly activate before those fields exist or are interactable —
Angular Material tabs (`mat-tab-group`/`mat-tab`), signal/state-driven
wizard steps (e.g. `*ngSwitch="step()"` with multiple `*ngSwitchCase`
blocks), accordions, or conditional panels. This is structurally
significant, not cosmetic: fields inside a lazily-rendered tab or an
inactive wizard step may not exist in the DOM at all until that
section is activated, so every field/loop/table you report as belonging
to one of these sections must be linked back to it.

For every such section found in the primary screen, report it in
"screen_sections":

- section_type: one of "tab", "step", "accordion", "conditional_panel"
- section_label: the visible label for this section, resolved per TEXT /
  LABEL RESOLUTION above if rendered via i18n
- order: this section's position/index among its siblings
- activator: the object for the clickable element that activates this
  section (data_cy, id, preferred_locator) — "Unknown" if the section has
  no distinct clickable locator (common: zero data-cy anywhere in the
  file, as with plain mat-tab-group tab headers)
- activation_required: true if content is not guaranteed present in the
  DOM until this section is activated (true for standard Angular
  Material tabs and any *ngSwitch/*ngIf-gated step), false only if you
  can confirm from source that all sections render simultaneously
- entry_condition: for signal/state-driven steps, the raw source
  condition that gates this section (e.g. "step() === 2"); empty string
  if not applicable/not determinable
- contains_control_names: the control_name/loop_source/grid_name values
  (as reported elsewhere in this same output) that belong inside this
  section, so downstream agents can tell which fields require which
  section to be activated first

Do not fold tabs/steps/accordions into "other_components" — they belong
here specifically because of the activation-order dependency they create
for every field/action nested inside them, which other_components does
not capture.

`hidden` vs. `visibility_condition` — these are two different things and
both must be considered:
- `hidden`: a simple boolean for the STATIC case — true only if the field
  is unconditionally hidden (e.g. permanently removed via a fixed flag),
  false otherwise, including for fields whose visibility depends on
  runtime data (see next bullet).
- `visibility_condition`: the raw source expression from the field's
  `*ngIf`/`*ngSwitchCase`/equivalent directive, when visibility depends on
  something other than a static always-shown/always-hidden state — for
  example `*ngIf="BiztransactionData.BIZTransactionTypeIsGoodQuantity !=
  1"`. Report the expression as written in source; do not attempt to
  evaluate or resolve it to true/false, since its actual runtime value
  depends on master/business data not available from static source
  analysis. Leave this as an empty string when the field has no
  conditional visibility beyond the `hidden` flag. This tells downstream
  agents that a field's presence in the DOM cannot be assumed constant
  and must be checked/handled per test scenario, rather than silently
  treating it as always-present because `hidden` alone reads false.

Otherwise return false.

Do NOT invent lookup sources.

LOOP / REPEATING STRUCTURE ANALYSIS (CRITICAL)
--------------------------------------------------

If the primary screen's source contains a loop that generates repeated
UI elements — an Angular `*ngFor`, a FormArray-driven row template, a
signal/computed-function-driven loop (see COMPONENT CLASSIFICATION
above), or any other repeating structure — this is NOT the same thing as
a single static field, and must never be collapsed into one. Report it
as its own loop entity, separate from the FIELD ANALYSIS and TABLE/GRID
ANALYSIS entries for the elements it generates.

BEFORE enumerating a loop's fields, read the FORM CONFIG (formjson)
RESOLUTION section above. If the loop is driven by a generic grid
component (gb-formgrid or similar) whose own template has no column
names, you MUST resolve the formjson Grid array for this field first —
the shared component's Angular source alone is structurally insufficient
to know how many distinct fields exist per row or what they are called.
Do not enumerate loop fields from the shared component's generic
variable names (`item`, `value`, `Field`) under any circumstance.

The critical detail to get right is that data-cy/id attributes inside a
loop are usually built dynamically, not hardcoded — for example:

  [attr.data-cy]="'ModuleName' + i + '-PickList'"

The RENDERED value at runtime is index-suffixed (ModuleName0-PickList,
ModuleName1-PickList, ...), but the SOURCE TEXT is a template expression,
not a literal string. You must recognize this pattern and report the
underlying PATTERN with an explicit index placeholder — do not report
just the static prefix as if it were the whole locator, and do not
invent a single generic field name to stand in for the whole loop (for
example, do not collapse a per-row Module dropdown and a per-row Default
Menu dropdown into one invented field called "Role Modules" — each looped
field gets its own pattern entry, resolved from the formjson Grid array
as described above, e.g. "ModuleName{index}-ComboBox" and
"DefaultMenuName{index}-ComboBox" as two separate field entries).

For every loop found, extract:

- loop_source: the array/collection/formArrayName/signal-function-call
  driving the loop (e.g. "RoleModuleArray", or "PeriodicRadio()" per
  COMPONENT CLASSIFICATION above)
- item_component: the component or element type repeated per iteration
- index_variable: the loop's index variable name as used in the template
  (e.g. "i")
- fields: for each distinct field repeated inside the loop, an object
  matching the shape of a normal FIELD ANALYSIS entry, except
  data_cy/id/name/preferred_locator use "{index}" as an explicit
  placeholder for the loop index (e.g. "ModuleName{index}-PickList")
- add_row_action: the action object (name, data_cy, id, preferred_locator)
  for whatever adds a new iteration, if one exists
- remove_row_action: the action object for whatever removes an iteration,
  with its own locator pattern including "{index}" if it is itself
  index-suffixed (e.g. "DeleteRow{index}")
- is_bounded: true if the loop has a fixed/maximum length determinable
  from source, false if it is open-ended (user can keep adding rows)

If a locator pattern cannot be confirmed from source (including after
checking formjson per the FORM CONFIG RESOLUTION section), use "Unknown"
for that field per the RULES below — do not guess the naming convention
from a different screen, from general Angular conventions, or from the
shared component's internal variable names.

Extract any dialogs explicitly found in the source:

- Lookup
- Search
- Selection
- Confirmation
- Delete
- Approval

For each dialog found, extract:

- Dialog Type (one of the categories above)
- Trigger Action (the business action or row action that opens it, if identifiable)
- Confirm Button — an object with data-cy, id, and Preferred Locator
- Cancel Button — an object with data-cy, id, and Preferred Locator

CONFIRMATION DIALOGS OFTEN LIVE ENTIRELY INSIDE A SHARED COMPONENT'S OWN
ACTION HANDLER, NOT IN THE PRIMARY SCREEN'S FILE — READ BEFORE SKIPPING A
BUSINESS ACTION AS "NO DIALOG FOUND": for actions rendered by a shared
business-action/button-bar component (gb-formaction or similar — see
COMPONENT COVERAGE), the confirmation dialog for that action (typically
Delete, sometimes Clear/AddNew/Reset) is frequently implemented entirely
inside that SHARED component's own .ts click-handler method for the
action — e.g. a `dialog.open(GbDialogBoxComponent, { data: { message:
"Do you want to Delete...", heading: 'Confirmation', button1: 'Yes',
button2: 'No' } })` call that only fires the primary screen's own
FormOutput('Delete') after the user confirms. This is genuinely part of
the primary screen's Delete action (see the PRIMARY SCREEN EXCEPTION
above) even though no matching code exists anywhere in the primary
screen's own file. Whenever a business action is reported with a shared
component as its locator source, you MUST also check that shared
component's own handler method for the SAME action for a gated
`dialog.open(...)` call, and report it here with trigger_action set to
that business action's name — do not report "no dialog" for Delete/Clear/
AddNew actions solely because the primary screen's own file shows none.

Only include a confirm/cancel button object if the source actually shows
one for that dialog — use "Unknown" for any locator field you can't
determine, per the RULES below. Do not invent a dialog that isn't present
in the source just to have something to fill in here.

Confirmation dialogs are frequently plain library components with buttons
that carry NO data-cy at all — only visible text (e.g. "Yes"/"No"). This
is a legitimate, common case, not a gap to fill by inventing one. If the
source shows the button has no data-cy/id, report data_cy and id as
"Unknown" and set preferred_locator to a text-based description you can
confirm from source (e.g. "text: Yes") rather than fabricating a data-cy
value that doesn't exist in the source at all. The exact button label
text (e.g. "Yes"/"No") must be read from the actual `button1`/`button2`
(or equivalent) values at the specific call site for this action — do not
assume "Yes"/"No" generically; confirm the literal strings passed at that
call site (resolved per TEXT / LABEL RESOLUTION above if rendered via
i18n), since different actions or screens may use different labels (e.g.
"Confirm"/"Cancel", "OK"/"No").

--------------------------------------------------
FUNCTIONALITY / CODE BEHAVIOR ANALYSIS (CRITICAL — FRONTEND-OBSERVABLE ONLY)
--------------------------------------------------

Everything above this section captures WHAT UI elements exist and WHERE
their locators are. This section captures WHAT THE SCREEN ACTUALLY DOES —
its execution flow, method behavior, conditional logic, frontend service
interactions, and data transformations — so downstream agents can write
test cases and scripts that verify real behavior, not just element
presence. This is derived ENTIRELY from the primary screen's own
component/service TypeScript (plus directly-referenced frontend service
files) — see FRONTEND-ONLY SCOPE above. Never infer or describe backend
processing; describe only what the frontend code does before sending a
request and after receiving a response.

For the primary screen, populate "functional_behavior":

- lifecycle_hooks: for each Angular lifecycle method implemented
  (ngOnInit, ngOnDestroy, ngAfterViewInit, etc.) that contains meaningful
  logic (not just injection/no-ops), an object:
  { "hook": "", "description": "" } — description is a concise,
  plain-language account of what actually happens (e.g. "if an existing
  record ID is present and this is not an Add-New flow, loads that
  record's data via the picklist load path and marks the form
  non-editable").

- event_handlers: for each method bound to a template event (click,
  change, output emitter such as (FormOutput), (PicklistValue), (change),
  (DateOutPut), etc.) in the primary screen's own template, an object:
  { "trigger": "", "method_name": "", "description": "",
    "conditions": "", "calls_service_method": "",
    "resulting_ui_effect": "" }
  - trigger: the exact binding as written (e.g. "(FormOutput)")
  - method_name: the handler method's name
  - description: plain-language summary of what the method does, in the
    order it does it
  - conditions: any branching that changes behavior (e.g. "different
    handling for event === 'Save' vs 'Delete' vs 'AddNew'"); empty string
    if the method has no branching
  - calls_service_method: the frontend service method it calls, if any
    (e.g. "CostAnalysisservice.formsaveservice"); empty string if none
  - resulting_ui_effect: what the user observably sees happen as a result
    (e.g. "opens a success dialog, then resets the form and clears the
    picklist cache")

- conditional_business_logic: for every if/else, switch, or reactive-form
  cross-field rule that determines differing behavior based on form state
  (not simple required/format validators already captured under
  VALIDATION ANALYSIS), an object:
  { "condition_source": "", "description": "",
    "affected_fields_or_actions": [] }
  - condition_source: the raw source expression/snippet the logic is
    based on (e.g. "date1 && date2 && date1 > date2")
  - description: plain language (e.g. "if the From date is after the To
    date, both dates are reset to today and an info dialog is shown")
  - affected_fields_or_actions: control_name(s)/action_name(s) impacted

- frontend_service_calls: for every frontend service method call
  triggered from this screen (save/update/delete/load/etc.), an object:
  { "trigger_point": "", "service_method": "",
    "request_data_summary": "", "response_handling": "" }
  - trigger_point: what causes the call (e.g. "Save button click via
    FormOutput('Save')")
  - service_method: the exact method reference (e.g.
    "CostAnalysisservice.formsaveservice")
  - request_data_summary: what is sent, in plain language, based only on
    what the frontend code assembles (e.g. "the full reactive form's
    current value"); do not describe backend processing of it
  - response_handling: what the frontend does with the response — success
    path, error path, and any UI effect (dialog, form reset, navigation),
    based only on what the .subscribe()/.then() handler in the frontend
    code actually does

- data_transformations: for any place the primary screen's own code
  transforms data before sending it or after receiving it (date/epoch
  parsing, computed/derived field values, form value reshaping before
  submit, response reshaping before patchValue), an object:
  { "description": "", "source_reference": "" } — source_reference is the
  method/property name where this happens (e.g.
  "getDateFromEpochString")

- functional_summary: a concise, plain-language, end-to-end narrative of
  what this screen does for a user — from opening it, through entering/
  loading data, through each business action's outcome — synthesizing the
  above into a readable account. This is not a restatement of the field
  list; it is the behavioral story the field list and locators exist to
  support testing. Base it strictly on what the frontend source actually
  implements; do not describe steps, validations, or outcomes that are
  not present in the supplied source.

If the primary screen's own .ts file is thin (e.g. a pure routing/report
wrapper with no real handler logic), report functional_behavior with
mostly-empty arrays and a functional_summary that honestly reflects that
minimal behavior — do not pad it with invented logic to make the section
look complete, per the PRIMARY SCREEN section's existing guidance against
substituting more detailed reference content for a thin primary screen.

AUTOMATION READINESS (page-level summary)
--------------------------------------------------

After completing FIELD, LOOP, TABLE, DIALOG, and SCREEN SECTIONS analysis
for the page, report one summary object, "automation_readiness":

- locator_coverage: "full" (nearly all interactive elements resolved to a
  real data-cy/id), "partial" (a meaningful mix of resolved and
  "Unknown"), "minimal" (a small minority resolved, most "Unknown"), or
  "none" (effectively zero data-cy/id anywhere in the primary screen's
  own source)
- coverage_notes: a short, concrete note explaining the rating (e.g. "0
  of ~40 interactive elements across 10 tabs carry a data-cy attribute;
  every locator in this output is Unknown")
- requires_source_changes: true if reliable automation of this screen, as
  currently written, is not realistically achievable without adding
  locators/attributes to the source first; false otherwise

This is a summary signal, not a substitute for reporting "Unknown"
individually wherever it belongs elsewhere in the output — both must be
done.

RULES
--------------------------------------------------

- Never invent information.
- Never assume missing functionality.
- If information cannot be determined, return "Unknown".
- Never output a schema/field name (e.g. the literal string "data-cy",
  "id", or "value") as if it were a resolved locator value — this is a
  guessing failure identical in severity to fabricating a plausible-
  looking one, and must be treated as "Unknown" instead.
- Never assume a dynamically-built attribute's underlying value (e.g. a
  Field.Name, a Grid column's "value", or a menu node's "level") is equal
  to something visible elsewhere (a formControlName, a variable name, an
  assumed depth of 0/1) without confirming it from the actual config/data
  source that supplies it, per FORM CONFIG RESOLUTION and the navigation
  hop-level guidance above.
- Never invent a human-readable label for an i18n translation key that
  could not be resolved against a supplied translation source — report
  the key itself and flag it as unresolved per TEXT / LABEL RESOLUTION.
- Never fill backend-related fields (backend_framework, database,
  authentication_method beyond what frontend code shows, rest_apis beyond
  called endpoint paths) with inferred/typical values — "Unknown" is the
  correct, expected output when the frontend source does not reveal them.
- Never describe backend implementation, database behavior, or API
  internals in functional_behavior — only frontend-observable request
  intent and frontend-observable response handling.
- Ignore node_modules, dist, build, .git, .venv and __pycache__.
- Base every answer ONLY on the supplied source code.
- Return one module object per module.
- Return one page object per page.
- Return ONLY valid JSON.
- No markdown.
- No explanations.
- No comments.
